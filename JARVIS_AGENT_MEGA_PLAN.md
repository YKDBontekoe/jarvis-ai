## Checkpoint 2: A2 project outcome and next action, A3 search

- **A2.** `projects` gains `outcome`, `status` (active/completed/archived), `next_action_type/id/note` (migration `AddProjectFocus`). `PUT /projects/{id}/focus` replaces outcome and next action only; the old edit form cannot wipe them (tested). `ProjectFocusService` checks the linked commitment/decision/reminder/task is the owner's and reports its state (open/done/gone); tools `GetProjects`, `SetProjectOutcome`, `SetProjectNextAction`; the project context now carries the outcome, next action and project id. App: "Outcome and next step" card + edit sheet (link one of your promises), done/gone states. A personal to-do is a commitment; an agent task is a task and stays distinct.
- **A3.** New providers: people (notes matched but never shown), promises (suggested ones labelled), decisions. All use `SearchRanking.Best` (relevance, then newest, then title) so which hits survive the limit no longer depends on repository order; the six older in-memory providers were changed to it too. Query matching ignores accents.
- **F02.2.** `messages.content` trigram index (migration `AddMessageContentSearch`); `ConversationStore.SearchMessagesAsync` is owner-joined, user/assistant only, task conversations excluded. `GET /conversations/{id}/messages?around=` and `?after=` page both ways with the (created, id) tiebreak. App: `MessageContextScreen` opens the hit highlighted for ~3 s with earlier/later paging and "Open chat". Decision: open-at-match is a read-only context view instead of changing the live chat's scroll machinery, so the composer and a streaming reply are never disturbed.
- **Profile scope decision (F02.2.5).** Message hits are for the owner's own search screen. The agent's `SearchEverything` removes the `message` kind, so a restricted profile never reads other chats through it. People/promises/decisions are exposed to the agent like memories already are.

## Checkpoint 3: A4 ask about a source, A8 memory review and correction

- **A8.** `memories.superseded_by_id` (migration `AddMemorySupersession`) links a replaced memory to its replacement, so a correction keeps a readable chain. `MemoryReviewRules` (pure) lists current memories that were learned lately by Jarvis, have confidence below 0.6, or expire within 14 days; pinned memories are listed but never replaced. `MemoryReviewService` resolves each memory's source (the chat and message it came from, only for the owner), the profile name, and the number of corrections. API: `GET /memory/review`, `POST /memory/{id}/correct|expire`, `GET /memory/{id}/history`. A correction goes through the existing `ReplaceAsync`, so the old memory's `valid_until` and graph facts end with it and search finds only the correction (integration-tested against Postgres). Tool `CorrectMemory` (no approval: it keeps history and refuses pinned memories). App: Review memories screen with Correct / No longer true / history / "See where" (opens the A3 message context view).
- **A4.** `POST /files/{id}/ask` creates a chat bound to the chosen profile with the file as its only source; a profile that restricts files to collections cannot be widened (409). App: "Ask Jarvis about this" in Files; the chat shows the source chip, which can be removed (existing behaviour).
- **Decision.** Opening a chat "with a source selected" reuses conversation sources; a Library item is not a conversation source today, so Ask from Library is not done.

## Checkpoint 4: A7 editable comparison

- **Contract.** `comparisons` table (id, owner, title, project, library item, `definition` jsonb; migration `AddComparisons`). `ComparisonCalculator` (pure, `Application/Comparisons`): per option the weighted average over *known* criteria, `coverage` = known weight share, unknown never zero, ties within 0.05, ties broken by name so the same input always gives the same ranking, sensitivity = would removing one criterion change the leader, warnings (nothing to rank, mostly unknown, tied leaders). `ComparisonValidator` trims and limits (12 criteria, 8 options).
- **Service.** Create/update (the decision link belongs to the server: an edit cannot forge or drop it), `SetCell` by id or name, `SaveToLibrary` (a tagged `report` note whose Markdown keeps unknowns, notes, dated sources and what could change the answer), `Decide` (logs one decision with the score and unknowns in its context; same option again returns the same decision; a different option is 409; nothing is bought or sent).
- **Agent.** Tools `CreateComparison`, `SetComparisonCell`, `GetComparison` (group `comparisons`): the model records evidence and does not do the arithmetic; the tool text says to leave a cell out when it is not known.
- **App.** Comparisons list + detail: ranking cards (tied / mostly unknown / chosen), sensitivity notice, weight sliders, per-option evidence cells with a "I know this" switch (off = unknown), source and date, Save to Library, Choose this one (sheet: how sure + review date). Large text fixed after the first screenshot squeezed the option name; the ranking row now wraps.
- **Decisions.** Storage is a new table rather than a Library note because weights and cells must be edited and recomputed; the Library gets the rendered report. No new entity type, so a comparison is reached from Comparisons, quick commands and `comparison:{id}` destinations, not yet from search or related views.
- **Tests.** Unit 1745 pass (`ComparisonTests` 10, `ComparisonServiceTests` 9); integration `ComparisonPersistenceTests` (1); Dart `comparisons_test` (6), full `flutter test` 750 pass, analyze clean. Real stack: `comparison_flow` (create, rank, cell edit, determinism, Library report, decide once, 409, link preserved) plus the earlier flows. Screenshots: `build/screenshots/audit-{phone,small,large-text}-comparison:c1.png`.

## Checkpoint 5: A5 meeting prep, A6 debrief, F22 first slice

- **Contract.** `meetings` table (owner, title, start, project, `document` jsonb; migration `AddMeetings`). The document holds participants, agenda lines (each `shared` or private), private notes, the prep pack, the debrief text and the candidates.
- **Prep (`MeetingPrepBuilder`, pure).** From the owner's own records only: project outcome and next step (A2), open accepted promises with the participants (overdue first, capped), unresolved decisions that mention a participant or the project, project files, what earlier meetings with the same people or project left unanswered or unreviewed. Every fact has a `ref`; anything missing becomes a question (template-specific for one-on-one, project update, interview, decision). The agenda is only filled when empty, so a refresh never overwrites the owner's agenda.
- **Debrief (`MeetingDebriefExtractor`, pure, rule-based, English and Dutch).** Decisions ("we decided", "besloten"), what I owe ("I'll", "ik stuur"), what a named participant will do, and questions. Dates: ISO, today/tomorrow, weekdays, day-month in both languages; a vague date ("next week", "end of the month") is kept as wording with no day. Ids are stable per kind and sentence, so a second read keeps earlier choices. Text is untrusted data: a hidden instruction produces nothing, and an injected promise is only a pending proposal (tested).
- **Acceptance.** `AcceptAsync` calls `ICommitmentService.CreateAsync` (source `meeting`) or `IDecisionService.CreateAsync` (the owner must give confidence and a review day); accepting twice creates one record; a question cannot be accepted; an accepted candidate cannot be dismissed; dismissing changes nothing but the candidate.
- **Follow-up.** Built only from accepted items and shared agenda lines; private notes, private lines and unaccepted items are excluded; `sent` is always false and there is no send endpoint.
- **Agent.** Tools `PrepareMeeting`, `DebriefMeeting`, `DraftMeetingFollowUp` (group `meetings`); the debrief tool only lists proposals and tells the user to accept in the app.
- **App.** Meetings list with calendar events, creation sheet, detail screen as described in the architecture doc.
- **Decision.** The debrief uses rules instead of a model so the demo is deterministic and works with no provider; a model reading remains a later addition behind the same candidate contract. Meetings are not yet an `EntityType`, so a meeting is reached from the Meetings screen, quick commands and prep refs (`meeting:id`), not search.
- **Tests.** Unit 1781 pass (`MeetingExtractionTests` 24, `MeetingServiceTests` 12); Dart `meetings_test` (11), full `flutter test` 761 pass, analyze clean. Real stack: `meeting_flow` (prep from seeded records, agenda kept on refresh, debrief creates nothing, accept once, edited acceptance, decision needs confidence, dismiss, unsent follow-up without private text, bad input) plus all earlier flows. Screenshots: `build/screenshots/audit-{phone,small,large-text}-meeting:m1.png`.
- **Not done.** Calendar write-back, recording or transcription, calendar-event identity beyond title and start (F22.1 stable link), proposed time blocks for accepted follow-through (F22.7), people-page open loops (F22.8 beyond the prep carry-forward), a model-based extraction, search for meetings.

## Checkpoint 6: A10 weekly review follow-through

- **What.** `WeekFollowThroughBuilder` (pure) counts the week in the owner's local Monday–Sunday from the actual records: accepted promises fulfilled or dropped that week (by local completion day), overdue and a-week-or-more overdue, decisions due next week, active projects with no next step or a finished one. Items behind each count are listed and capped. At most three suggestions, in a fixed order: give the most overdue "I owe" promise a new day, choose a project's next step, then the second overdue promise.
- **Read-only generation.** `GET /reviews/weekly/follow-through` creates nothing (tested at service level and on the real stack). Accepting changes exactly one existing record: `plan_commitment` updates a promise's due day through `ICommitmentService.UpdateAsync` (its morning reminder follows; the same day again is a no-op); `project_next_step` goes through `IProjectFocusService.SetAsync` and keeps the outcome. Dismissed suggestions are kept in the owner settings section `weekly-review.followthrough` for 28 days.
- **App.** A follow-through card on the weekly review (for the selected week): counts, items that open the real record, a quiet week says so, suggestions with the day or note chosen by the owner, "Not now".
- **Tool.** `GetWeekFollowThrough` (read-only).
- **Tests.** Unit 1794 pass (`WeekFollowThroughTests` 13); Dart `follow_through_test` (6), existing `weekly_review_screen_test` unchanged and passing, full `flutter test` 767, analyze clean. Real stack: `week_follow_through_flow` (counts reconcile, reading creates nothing, plan moves one promise with a reminder, project step keeps the outcome, dismiss, 400/404 cases).
- **Not done.** Accepting into the day planner or as a project-linked reminder (F05), a "keep/change/stop" review of habits (F23.7), the narrator mentioning follow-through, widgets/briefings using the same counts (F01.1.7 beyond Home).

## Checkpoint 7: F05 promise → time on today's plan

- **What.** `POST /planner/today/items` and the `AddToDayPlan` tool accept a `commitment:<id>` source. `DayPlannerService` checks it through `ICommitmentService.GetAsync` (owner scoped; unknown, another owner's, suggested, done or dropped promises are refused with 400), uses the promise description as the title when none is given, and returns the existing open to-do if the same promise was already planned, so asking twice never doubles the time. Items carry `sourceRef` (backward compatible: the settings JSON simply lacks it for older items).
- **Placement.** Unchanged: the existing deterministic `PlanMyDay` puts the to-do in the earliest free block. Nothing is written to the calendar, and finishing the to-do does not close the promise (the owner says it is done in Inbox).
- **App.** Inbox promise cards get "Plan today" (accepted promises only; shows the server's reason when refused); Today labels such to-dos "From a promise".
- **Tests.** Unit `DayPlannerTests` (+7: title from promise, dedupe, replan after done, explicit title wins, bad source, other owner/suggested/closed, promise stays open); Dart `inbox_screen_test` (+2), `day_planner_test` (+1). Real stack: `planner_commitment_flow` passes.
